Detecting Layout Changes in Web Archives

Identifying structural shifts across 12 years of Greek news websites

Since we know which data we want to use for downstream processing, it's time to create scrapers that extract the headlines (and their links) from the home pages. However, the HTML code (and the layout) of the main pages changed from time to time. Therefore, we will try to detect automatically when these layout breaks occur. This is essential not only for predicting possible silent scraper failures, but also for determining the feasibility of the rest of the project! Even with LLM assistance, creating scrapers and testing them can be a tedious process. Fortunately, the distinct layouts used in the last 12 years by the 8 sources were not too many.

In order to compare the layout of different HTML files, we need a metric for "layout similarity". With such a metric, we will be able to use a clustering algorithm and hopefully the clusters will indeed correspond to the different layouts.

A very reasonable way to go about creating this similarity metric is to compare the HTML structure of two webpages. Specifically, discard all of the uninteresting parts of the webpage (that the scraper will ignore) and then compare the parse trees left. Basically, if the sequence of html tags is similar enough, we expect that the layout has not changed in a major way and that the scraper will keep working. The problem with this approach is that we cannot just count how many tags are the same and then stop when we find the first discrepancy. A small additional chunk of code is probably insignificant, even though it creates a difference in the html tags. We need to compare chunks of the one html structure to chunks of the other html structure and see how much of each structure is contained somewhere (anywhere!) in the other one. Thus, we need to use the Levenshtein difference or a similar metric. The Levenshtein difference compares two strings (therefore we need to put the website's HTML tags in a string) and it measures how many changes (deletions, additions, replacements) it takes to convert one string to the other. However, exactly because any chunk of the one string must be compared to differently placed chunks of the other string, the computational cost is quadratic. This made the approach not run efficiently, even for a very small subset of the dataset, with only 5 webpages.

We thus turn to a more high-level approach, that uses statistics about the HTML tags, rather than treating each HTML tag individually during the comparison. We could simply compare how many times each tag appears in the snapshots. However, this treats all tags as equally important. Therefore tags such as <div>, that are very common and may change without great implications would dominate the metric. A more standardised way to give each tag the importance it deserves is the TF-IDF metric: For each tag, it measures how many times it appears in the document, but it multiplies it by one over the times that the tag appears in the whole database. Therefore, the prevalence of each tag is measured with respect to its overall prevalence.

This provides us with a statistical encoding of a snapshot's structure. We can then make a standardised list of all the HTML tags that are present in the snapshots and calculate for every snapshot the TF-IDF score of each of these tags (for the rare tags the score will often be zero). Moreover, we can even calculate the score for pairs of consecutive tags, to better capture the structure of the website (as an example, an increase in <p> tags and an increase in <h3> tags is a very high-level metric, but an increase in <h3> tags followed by <p> tags tells us that the scraper may fail to continue locating the headlines). Now every snapshot's structural statistics are saved in standardised vectors, which can then be easily compared. The code that computes the vectors follows:

The next step is to find an effective (for our use case) clustering algorithm. Since we do not know the number of clusters in advance, the two main options are Affinity Propagation and Agglomerative Clustering. Affinity Propagation assigns locally (for each point in the dataset) an element that can work as a "center" for its cluster. Subsequently, the local information about cluster-like structures is synthesized into a global picture, of a number of final clusters. The problem with this method is that the number of clusters we'll end up with could be unpredictable. Some small changes in the websites (that do not come close to breaking the scraper) are to be expected from time to time. We could thus end up with a way too sensitive cluster splitting and there would be no easy way to judge from a simple graph of the clusters whether the changes are actually deep enough to break a scraper.

On the other hand, agglomerative clustering uses a much better suited approach. It compares the distances of the points and merges the two closest ones into a cluster. Once such clusters have begun to form, they can also be merged with other points (or clusters). The distance from a cluster is usually expressed as the distance from its centroid (the average of the cluster's vectors). The advantage of this method lies in that it creates the clusters step by step (and, if allowed to continue, the algorithm will merge everything into one big cluster!). Therefore, we are the ones to choose how dissimilar two clusters should be, in order to not be merged in a bigger cluster. For our use case, we use to measure the similarity (or the "distance") the cosine similarity and we expect that a scraper will fail if relatively small but significant changes in the layout happen. Given the numerical amplification of the changes that is brought about by TF-IDF, we stop merging when cosine similarity surpasses 0.2.

The function that implements these ideas is the following:

def analyze_site_clusters(html_files):
    """
    Converts HTML files to TF-IDF vectors and clusters them to find layout eras.
    """
    # 1. Convert all files into structural strings
    dom_strings = [get_dom_string(f) for f in html_files]
    
    # 2. Vectorize the strings using N-grams 
    # ngram_range=(1,2) tracks both individual elements and parent->child relationships
    vectorizer = TfidfVectorizer(ngram_range=(1, 2), min_df=1)
    vectors = vectorizer.fit_transform(dom_strings)
    
    # 3. Agglomerative Clustering
    # Convert sparse TF-IDF matrix to dense array for AgglomerativeClustering
    dense_vectors = vectors.toarray()
    
    # distance_threshold=0.2 means: only create a new cluster if 
    # the vectors are more than 20% different. 
    # n_clusters=None is required when using a distance_threshold.
    clustering = AgglomerativeClustering(
        n_clusters=None, 
        distance_threshold=0.2, 
        metric='cosine', 
        linkage='average'
    )
    labels = clustering.fit_predict(dense_vectors)
    
    # 4. Find the chronological breaks
    breaks = []
    for i in range(1, len(labels)):
        prev_cluster = labels[i-1]
        curr_cluster = labels[i]
        
        if prev_cluster != curr_cluster:
            breaks.append({
                "time_of_break": format_timestamp(html_files[i]),
                "transition": f"Cluster {prev_cluster} -> Cluster {curr_cluster}",
                "previous_file": os.path.basename(html_files[i-1]),
                "changed_file": os.path.basename(html_files[i])
            })
            
    return labels, breaks
